# HANDS-003 課題

## 課題概要

Templateに含まれるCore Platform / UIとアプリThemeの接続を読み解き、既存の共通部品をFeatureから利用するための前提を理解する。

この課題の目的は、Android依存処理を増やすことではない。共通部品をどこへ置き、どの層から使い、どこに依存を閉じ込めるかを理解することである。

## 背景

Templateには、SampleAppで利用する共通部品の多くがすでに含まれている。

- `StringProvider`
- `RawResourceReader`
- `DateTimeProvider`
- `AppClock`
- `DispatcherProvider`
- `CoroutineScopeProvider`
- `AppLogger`
- `ExternalUriOpener`
- `RouteArgumentEncoder`
- `AppDialog`
- `LoadingContent`
- `BaseAppTheme`
- `BaseThemePreset`
- `BaseThemeRegistry`

そのため、これらのクラスを別名で作り直したり、Feature側へContextやAndroid APIを直接渡したりしてはいけない。

## 実施内容

### 1. ModuleとDIの構成を確認する

次のファイルを読み、Moduleの責務と依存方向を整理する。

- `BaseArchitecture/settings.gradle.kts`
- `BaseArchitecture/core/platform/build.gradle.kts`
- `BaseArchitecture/core/ui/build.gradle.kts`
- `BaseArchitecture/core/platform/src/main/java/jp/co/nsco/basearchitecture/core/di/CoreModule.kt`
- `BaseArchitecture/core/ui/src/main/java/jp/co/nsco/basearchitecture/core/ui/theme/ThemeUiModule.kt`

次の内容を自分の言葉で説明する。

- `core:platform`にAndroid依存処理を閉じ込める理由
- `core:ui`にCompose UI共通部品を置く理由
- interfaceとAndroid実装を分ける理由
- Hilt Moduleが担う役割

### 2. Providerの利用経路を追跡する

次のProviderについて、interface、Android実装、DI登録、利用側を確認する。

- `StringProvider` / `AndroidStringProvider`
- `RawResourceReader` / `AndroidRawResourceReader`
- `DateTimeProvider` / `AppDateTimeProvider`
- `AppClock` / `SystemAppClock`
- `DispatcherProvider` / `AppDispatcherProvider`
- `CoroutineScopeProvider` / `AppCoroutineScopeProvider`

各Providerについて、次を記録する。

```text
契約:
Android実装:
DI登録:
利用側:
ViewModelやFeatureへ直接Android依存を渡さない理由:
```

### 3. LoggerとCoroutineを確認する

次の内容を確認する。

- `AppLogger`がログ出力の契約だけを持っていること
- `AndroidAppLogger`がTimberへ委譲していること
- `AppLoggingInitializer`がApplication起動時の初期化を担当すること
- `DispatcherProvider`でDispatcherの差し替えが可能になること
- `CoroutineScopeProvider`でFeatureが任意のCoroutineScopeを乱立させないこと

Applicationの初期化処理と、Featureから利用する場合の依存経路を図にする。

### 4. Navigation補助と外部URIを確認する

次のファイルを確認する。

- `RouteArgumentEncoder.kt`
- `ExternalUri.kt`
- `ExternalUriOpener.kt`
- `AndroidExternalUriOpener.kt`

次の違いを説明する。

- Route引数のencodeだけを補助すること
- Coreが`NavHost`や`NavController`を抽象化しないこと
- 外部URI起動をViewModelが直接Contextで行わず、契約経由で扱うこと

### 5. DialogとLoadingを確認する

次のファイルを確認する。

- `DialogUiState.kt`
- `AppDialog.kt`
- `LoadingContent.kt`

次の処理をどの層が担当するかを整理する。

- Dialogを表示するかどうかを決める
- Dialogの文言を解決する
- positive / negative / dismissのcallbackを受ける
- Loading中に表示する内容を決める
- Loading状態を自動で切り替える

特に、Core UIは表示部品を提供するだけで、Featureの業務判断や自動状態管理を持たないことを確認する。

### 6. Themeの適用経路を確認する

次のファイルを確認する。

- `app/src/main/java/jp/co/nsco/basearchitecture/ui/theme/Theme.kt`
- `app/src/main/java/jp/co/nsco/basearchitecture/app/AppRoot.kt`
- `core/ui/src/main/java/jp/co/nsco/basearchitecture/core/ui/theme/BaseAppTheme.kt`
- `core/ui/src/main/java/jp/co/nsco/basearchitecture/core/ui/theme/BaseThemePreset.kt`
- `core/ui/src/main/java/jp/co/nsco/basearchitecture/core/ui/theme/BaseThemeRegistry.kt`
- `core/ui/src/main/java/jp/co/nsco/basearchitecture/core/ui/theme/ThemeModeResolver.kt`

TemplateのDefault Themeを入口として、次の流れを図にする。

```text
AppRoot
  -> app側Theme Composable
  -> BaseAppTheme
  -> ThemeSettings / BaseThemeRegistry
  -> ColorScheme / Typography / Shapes / Spacing
  -> 配下の全Composable
```

その後、Previewまたはローカル確認用に、色・Shape・Spacing・ThemeSettingsのいずれかを一時的に変更し、画面へ反映されることを確認する。実験用の変更は最終的に戻す。

### 7. SampleAppとの差分を分類する

TemplateとSampleAppを比較し、差分を次の表へ分類する。

| 差分 | 03で確認するか | 後続Step | 理由 |
|---|---|---:|---|
| Providerの契約とDI | する | - | Core利用の前提だから |
| BaseAppThemeとThemeRegistry | する | 05 | Theme設定の保存・選択は後続だから |
| AppViewModel | 構造だけ確認 | 05 | アプリ共通Theme状態を扱うため |
| DataStore / Database / Network | しない | 04 | Storage / Network基盤の範囲だから |
| Markdown UI | しない | 07 | Legal / License画面で利用するため |
| Feature固有の文言・State・UseCase | しない | 05以降 | Feature実装の範囲だから |

差分を見つけたら、すぐに03へ取り込まず、対応表の後続Stepで解消する差分かどうかを判断する。

### 8. ビルドと自己レビューを行う

次の確認を行う。

```powershell
.\gradlew.bat :core:platform:test
.\gradlew.bat :core:ui:test
.\gradlew.bat :app:compileDebugKotlin
```

## 成果物

- Providerごとの利用経路メモ
- Module / DI / Themeの依存関係図
- TemplateとSampleAppの差分分類
- 一時的なThemeまたは共通UIの確認結果
- レビュー確認項目の自己チェック

## 禁止事項

- 既存Provider、Logger、Theme、Dialog、Loadingを別名で作り直さない
- ViewModel、UseCase、RepositoryへContextを直接渡さない
- CoreへFeature固有の業務ルールを追加しない
- CoreでNavigation全体を抽象化しない
- BaseViewModelへ自動Loadingや自動Error処理を追加しない
- DataStore、Room、Retrofit、Feature固有のTheme設定をこの課題へ持ち込まない
- 実験用の変更を最終ソースへ残さない
