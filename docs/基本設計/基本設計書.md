# 文書情報

## 1. 文書の目的

本書は、[BaseArchitecture 要件定義書](<E:/_work/_project/ProtoType/Android/BaseArchitecture/要件定義書.md>) で定義した要件を、Android / Kotlin / Jetpack Compose を利用したシステム構成へ展開するものである。

本書では、画面構成、Feature と Core の責務、状態管理、永続化、エラー、ログ、Navigation、DI などの基本方針を定義する。個別クラスの全プロパティ、SQL、細かな分岐、テストデータは詳細設計書で定義する。

## 2. 本書の位置づけと要件定義との関係

要件定義書は「何を実現するか」を定義し、本書は「要件をどの構造で実現するか」を定義する。

要件定義で利用者から観測できる振る舞いとして定義した内容を、Android の画面、状態、処理、データ境界へ展開する。実装クラス名やメソッドの細部は、必要な範囲を除き詳細設計へ委譲する。

### 2.1 要件定義からの変更点

現行ソースには、設定、履歴、テーマ、ライセンス、法務文書、バージョン情報まで実装されているため、本書ではそれらを基本設計の対象とする。

一方、通知配送、実認証、実キャッシュ、実サービスの最新バージョン API は要件定義で対象外または未確定としているため、本書でも具体的な業務処理は定義しない。

### 2.2 未確定事項

- 最新バージョン情報の本番取得先と認証方式
- 通知、ログイン時確認、キャッシュ保持設定の実機能への接続
- 操作履歴の正式な監査要件、保持期間、削除契機
- 案件適用時の認証・権限・個人情報要件
- 法務文書の正式版と改訂管理

# 1. システム構成

## 1.1 全体構成

```text
BaseArchitectureApplication
  -> AppRoot
      -> AppViewModel / ThemeRepository
      -> BaseAppTheme
      -> AppNavHost
          -> Feature Graph
              -> Route
                  -> ViewModel
                      -> UseCase / Facade / Reducer
                          -> Repository / Provider / Mapper
                              -> DataStore / Room / API / Android resource
```

AppRoot はアプリ共通のテーマと Navigation Host を構成する。Feature Route は ViewModel と Screen を接続し、個別の Navigation や UI 副作用を処理する。Screen は受け取った表示状態を描画し、操作をイベントとして通知する。

## 1.2 Module 構成

| Module | 主な責務 | 依存方針 |
|---|---|---|
| `:app` | Application、AppRoot、AppNavHost、Feature、アプリ固有 DI | Core を利用する |
| `:core:foundation` | 結果、エラー、Validation、Theme/認証契約 | 他 Core へ依存しない基礎層 |
| `:core:presentation` | 状態管理の共通契約と BaseViewModel | foundation を利用 |
| `:core:platform` | 時刻、文字列、Logger、Dispatcher、Scope、AppInfo | foundation を利用 |
| `:core:storage` | DataStore、Room 共通処理、Cache、Database | foundation を利用 |
| `:core:network` | API 応答、通信エラー、Interceptor | foundation を利用 |
| `:core:ui` | Theme、Dialog、Loading、Markdown | foundation を利用 |
| `:core:license` | OSS License 情報の契約・Android 実装 | foundation を利用 |

依存方向は App から Core へ向け、Core が App や Feature を参照しない構成とする。Feature 固有の Entity、DAO、業務ルールを Core に配置しない。

## 1.3 Feature 構成

```text
app/src/main/java/.../feature/
  sample/
  operationlog/
  legal/
  license/
  versioninfo/
```

Feature 内は原則として次の責務で分ける。

```text
presentation  : Screen / Route / ViewModel / State / Event / Message / Effect / Reducer
application   : UseCase / Facade
domain        : Domain Model / Policy / Repository 契約
data          : Repository 実装 / Mapper / DTO / Entity / LocalDataSource
di            : Feature 固有の Hilt 定義
```

## 1.4 共通依存

- Android Context を必要とする処理は ApplicationContext または Core の Provider に閉じ込める。
- ViewModel は Context、NavController、DAO、API を直接保持しない。
- 表示文言は String resource または StringProvider から解決する。
- 時刻は AppClock / DateTimeProvider を利用し、判定可能な形で差し替えられるようにする。
- 長寿命の CoroutineScope は Core の Scope Provider を利用し、画面処理には ViewModel または Compose のライフサイクルに紐付く Scope を利用する。

# 2. 共通処理フロー

## 2.1 共通シーケンス

```text
Screen / Route
  -> UiEvent を通知
BaseViewModel
  -> Event Channel へ追加
  -> 順次 handleEvent
ViewModel
  -> UseCase を呼び出す
  -> 成功・失敗を UiMessage へ変換
  -> Reducer へ dispatch
  -> 必要時に UiEffect を発行
Reducer
  -> 現在状態と Message から次状態を生成
Screen
  -> State を描画
Route
  -> Effect に応じて Navigation / Dialog / Snackbar を実行
```

## 2.2 共通アクティビティ

1. Route が ViewModel を取得する。
2. Route が State を購読し、Effect の購読を開始する。
3. Route が初期表示イベントを通知する。
4. ViewModel がイベントを順番に処理する。
5. 必要な UseCase がデータを取得・保存する。
6. ViewModel が処理結果を Message または Effect に変換する。
7. Reducer が State を更新する。
8. Screen が State を描画する。
9. Route が Effect を一度だけ実行する。

## 2.3 処理フローと設計要素の対応

| 処理 | 基本設計上の担当 |
|---|---|
| 表示 | Screen |
| 画面接続・Navigation | Route / Graph |
| 操作受付 | UiEvent |
| イベント順序制御 | BaseViewModel |
| アプリケーション処理 | UseCase |
| 状態変更理由 | UiMessage |
| 状態生成 | Reducer |
| 継続状態 | UiState |
| 単発処理 | UiEffect |
| 表示変換 | Presentation Mapper / Formatter |
| 保存・外部連携 | Repository / Gateway / Provider |

## 2.4 単発処理

Navigation、Dialog、Snackbar、外部 URI 起動は State に保持せず、Effect として Route へ通知する。Effect は replay せず、購読者がいない期間には再生しない。

# 3. 機能別処理フロー

## 3.1 Home

```text
Home Route
  -> Initialize
Home ViewModel
  -> Home Header UseCase
      -> 現在時刻取得
      -> 挨拶 Policy 判定
      -> Home Header 生成
  -> 表示文字列へ変換
  -> State 更新
  -> Home 表示ログ保存
```

取得失敗時は画面エラーを State に反映し、Dialog Effect を発行する。ログ保存失敗は Home 表示自体の失敗に連鎖させない。

## 3.2 履歴

```text
History Route
  -> Initialize
History ViewModel
  -> OperationLog 購読 UseCase
      -> Repository
          -> LocalDataSource
              -> Room DAO
  -> Domain Log を画面項目へ変換
  -> State 更新
Screen
  -> 検索・分類条件を Event 通知
  -> State の表示対象を再計算
```

Room の変更は購読結果として画面へ反映する。検索・分類は取得済みの画面表示項目に適用し、表示対象が空の場合は空表示を出す。

## 3.3 Settings

```text
Settings Route
  -> Initialize
Settings ViewModel
  -> Sample Settings / Theme Settings を購読
      -> DataStore Repository
  -> 選択肢を取得
  -> State 更新

設定変更
  -> Update UseCase
  -> DataStore 保存
  -> 成功: Message + Snackbar Effect
  -> 失敗: Message + Dialog Effect + エラーログ
```

Theme Settings は AppRoot が購読するため、設定画面以外も同じ設定を受けて再描画する。

## 3.4 法務文書

```text
Drawer
  -> 文書種別付き Route
  -> Document ViewModel
  -> Document UseCase
      -> Repository
          -> raw resource 読み込み
  -> Markdown を State へ反映
```

読み込み失敗時は Error State と Dialog Effect を出し、Retry Event で同じ文書を再取得する。

## 3.5 License

```text
License List
  -> License Provider
  -> LicenseInfo を一覧表示用へ変換
  -> 検索条件を State に保持
  -> License Click
  -> encoded licenseId 付き Detail Route
  -> License Detail Provider
  -> 本文を表示
```

## 3.6 Version Info

```text
Version Info
  -> AppInfoProvider から現在情報を取得
  -> LatestVersionRepository から最新情報を取得
  -> 現在値と最新値を比較
  -> VersionInfo を生成
  -> State へ表示
```

最新情報の取得に失敗しても、現在のアプリ情報を表示できる場合は確認失敗状態として継続する。外部ページ起動要求は Effect として Route へ通知する。

# 4. 状態遷移設計

## 4.1 状態設計方針

- UiState は画面を再描画するための継続状態を保持する。
- UiState は不変データとして扱い、Reducer から新しい値を生成する。
- Navigation、Dialog、Snackbar、外部 URI 起動は UiState に保持しない。
- 画面に必要な表示文字列、選択状態、エラー表示を UiState に保持する。
- Domain Model、Entity、DTO、Context、NavController を UiState に保持しない。

## 4.2 状態一覧

| 状態 | 意味 | UIの扱い |
|---|---|---|
| Loading | 初期取得中 | Loading 表示、必要に応じて操作制限 |
| Loaded / Ready | 表示可能 | 通常表示 |
| Empty | 表示対象なし | 空表示 |
| Error | 取得・保存等に失敗 | エラー表示、再試行や確認 |
| Updating | 設定等を保存中 | 保存処理中の表示 |

画面によって単独の enum ではなく Boolean、nullable 値、一覧、派生プロパティを組み合わせる。画面固有の状態表現は詳細設計で定義する。

## 4.3 状態遷移表

| 現在状態 | 契機 | 次状態 | 単発処理 |
|---|---|---|---|
| Loading | 取得成功 | Loaded | なし |
| Loading | 取得失敗 | Error | Dialog 等 |
| Loaded | 設定変更成功 | 更新後の Loaded | Snackbar |
| Loaded | 設定変更失敗 | エラー情報を含む Loaded/Error | Dialog |
| Loaded | 検索・分類変更 | 表示条件変更後の Loaded | なし |
| Loaded | 画面遷移要求 | 現画面維持 | Navigation |

## 4.4 Message と Effect の判断

| 事象 | Message | Effect |
|---|---|---|
| 取得開始 | Loading 更新 | なし |
| 取得成功 | データ・表示値更新 | なし |
| 取得失敗 | エラー表示値更新 | Dialog / Snackbar |
| 保存成功 | 保存結果・表示値更新 | Snackbar |
| 戻る | なし | NavigateBack |
| 詳細へ遷移 | なし | NavigateToDetail |
| 外部ページを開く | なし | OpenExternalUri |

# 5. 画面設計

## 5.1 画面一覧

| 画面 | 主な表示 | 主要操作 |
|---|---|---|
| Home | 挨拶、補足文、日付 | Drawer、Bottom Navigation |
| 履歴 | 検索欄、分類、履歴一覧 | 検索、分類、Drawer、Bottom Navigation |

| 法務文書 | 文書タイトル、Markdown 本文 | 戻る、再試行 |
| バージョン情報 | アプリ情報、更新状態 | 再確認、外部ページ、戻る |

## 5.2 画面遷移方針

```text
Home
  ├─ Bottom Navigation -> History
  ├─ Bottom Navigation -> Settings
  └─ Drawer -> Legal / License / Version Info

History
  ├─ Bottom Navigation -> Home / Settings
  └─ Drawer -> Legal / License / Version Info

Settings
  ├─ Bottom Navigation -> Home / History
  └─ Drawer -> Legal / License / Version Info

License List -> License Detail(licenseId)
```

AppNavHost は Feature Graph を束ねる。Feature Graph は画面 Route と引数を定義する。ViewModel は Navigation 実行主体を持たない。

## 5.3 共通 UI 仕様

- AppRoot で共通テーマを適用する。
- Top Bar は画面タイトルとメニュー操作を表示する。
- Bottom Navigation は履歴、Home、設定の3項目を表示する。
- Drawer はプライバシーポリシー、利用規約、ライセンス、バージョン情報を表示する。
- 共通 Dialog はタイトル、メッセージ、確認操作を表示する。
- Snackbar は保存成功などの短時間通知に使用する。
- Loading は画面の処理中状態を表示する。

## 5.4 入力項目仕様

| 画面 | 項目 | 形式 | 状態保持 |
|---|---|---|---|
| 履歴 | 検索文字列 | 文字列 | UiState |
| 履歴 | 分類 | enum | UiState |
| 設定 | Boolean項目 | Boolean | UiState / DataStore |
| 設定 | テーマモード | enum | UiState / DataStore |
| 設定 | テーマプリセット | typed ID | UiState / DataStore |

## 5.5 表示項目仕様

表示用文字列は Screen または Presentation の文字列解決部品で取得し、Domain / UseCase は Android のリソース ID や Context を知らない。

## 5.6 ボタン制御仕様

- 読み込み中の処理は、画面ごとの要件に応じて重複操作を抑制する。
- Retry は最後に読み込んだ対象を再実行する。
- 保存操作の成功・失敗は State と Effect を組み合わせて反映する。
- Screen はクリック時に Event を通知し、処理や Navigation を直接実行しない。

## 5.7 排他制御仕様

画面単位の Event は BaseViewModel が Channel で受け取り、受信した順に処理する。多重クリック抑制や Busy 中制御を全画面で必須化する自動処理は設けず、必要な Feature が State と Event に基づいて定義する。

## 6.5 License

ライセンス一覧を取得して表示し、名称またはライセンス名で絞り込む。選択されたライセンス ID を Route 引数として詳細画面へ渡す。

## 6.6 Version Info

アプリ自身の情報と最新確認結果を組み合わせる。最新取得に失敗した場合は現在のアプリ情報を維持し、確認失敗として表示する。ストアページとアプリ情報ページの起動は Route 側で実施する。

# 7. UseCase 定義

## 7.1 UseCase 責務補足

UseCase は一つのアプリケーション操作を表し、画面の UiState や Compose を知らない。外部アクセスは Repository、Provider、Gateway 等の契約を経由する。成功・失敗は `AppResult` で返す。

## 7.2 UseCase 一覧

| Feature | UseCase | 目的 |
|---|---|---|
| Sample Home | `GetSampleHomeHeaderUseCase` | 現在時刻から Home Header を生成 |
| Sample Settings | `ObserveSampleSettingsUseCase` | 設定値を購読 |
| Sample Settings | `UpdateSampleNotificationEnabledUseCase` | 通知設定更新 |
| Sample Settings | `UpdateSampleConfirmOnLoginEnabledUseCase` | ログイン時確認設定更新 |
| Sample Settings | `UpdateSampleKeepCacheEnabledUseCase` | キャッシュ保持設定更新 |
| Theme | `ObserveThemeSettingsUseCase` | テーマ設定を購読 |
| Theme | `UpdateThemeModeUseCase` | テーマモード更新 |
| Theme | `UpdateThemeIdUseCase` | テーマプリセット更新 |
| Theme | `GetAvailableThemePresetsUseCase` | テーマ候補取得 |
| Operation Log | `ObserveOperationLogsUseCase` | 操作履歴購読 |
| Operation Log | `GetOperationLogsUseCase` | 操作履歴取得 |
| Operation Log | `SaveOperationLogUseCase` | 操作履歴保存 |
| Operation Log | `DeleteOldOperationLogsUseCase` | 保持期間外ログ削除 |
| Legal | `GetLegalDocumentUseCase` | 法務文書取得 |
| License | `GetLicensesUseCase` | ライセンス一覧取得 |
| License | `GetLicenseDetailUseCase` | ライセンス詳細取得 |
| Version | `GetVersionInfoUseCase` | VersionInfo 生成 |

## 7.3 UseCase 処理ステップ

1. 入力を受け取る。
2. 必要に応じて Policy で条件を正規化・判定する。
3. Repository / Provider / Gateway を呼び出す。
4. Domain Model を組み立てる。
5. `AppResult.Success` または `AppResult.Failure` を返す。

## 7.4 CRUD / 外部 I/O マトリクス

| 対象 | Read | Observe | Create/Update | Delete |
|---|---|---|---|---|
| Sample Settings | 〇 | 〇 | 〇 | - |
| Theme Settings | - | 〇 | 〇 | - |
| Operation Log | 〇 | 〇 | 〇 | 〇 |
| Legal Document | 〇 | - | - | - |
| License | 〇 | - | - | - |
| Version Info | 〇 | - | - | - |

## 7.5 セッション内データ入出力

UseCase の入出力は Domain Model または意味のある入力値で表し、Screen の UiState、Room Entity、API DTO を直接受け渡ししない。

# 8. 業務ルール定義

## 8.1 基本方針

時間帯、履歴検索条件、保持期間、バージョン比較などの再利用可能な判定は Policy または Domain に分離する。ViewModel や Screen に判定式を重複させない。

## 8.2 入力・選択ルール

| ルール | 内容 |
|---|---|
| Greeting | 05:00-11:59 Morning、12:00-17:59 Afternoon、18:00-04:59 Evening |
| History Filter | All / Action / Setting / Error |
| History Query | 空白なら全件、入力時は title または summary の部分一致 |
| Operation Log Limit | 1未満は既定値へ補正、既定取得件数は50 |
| Retention Days | 1未満は既定値へ補正、既定保持日数は90日 |

## 8.3 保存・反映ルール

- 未保存の設定値は初期値を利用する。
- Sample Settings の初期値は3項目とも ON とする。
- Theme Mode の初期値は System、Theme ID の初期値は Default とする。
- テーマ変更は AppRoot を通じて全画面へ反映する。
- Operation Log のタイトルが空白の場合は保存しない。

## 8.4 Version 判定ルール

- 最新情報が取得できない場合は CheckFailed とする。
- 最新情報が取得でき、現在の versionCode が最新より小さい場合は UpdateAvailable とする。
- それ以外は Latest とする。
- 最新情報がなくても現在アプリ情報が取得できれば VersionInfo を生成する。

# 9. バリデーション定義

## 9.1 バリデーション一覧

| 対象 | 条件 | 結果 |
|---|---|---|
| Operation Log title | 空白でないこと | 空白なら Validation Failure |
| Route argument | 対応する識別子へ変換できること | 不正値は Feature 方針に従い既定値またはエラー |
| Operation Log limit | 1以上であること | 不正値は既定値へ補正 |
| Retention days | 1以上であること | 不正値は既定値へ補正 |
| History query | 文字列として扱えること | 空白は全件扱い |

## 9.2 バリデーション実行タイミング

- 入力値の即時表示が必要な場合は Presentation の入力処理で評価する。
- 保存可否に関わる条件は UseCase で再確認する。
- 保存前に不正値を検出した場合は、Repository へ渡さない。
- 固定された業務ルールは Policy でテスト可能にする。

# 10. エラー分類

## 10.1 エラー分類一覧

| 分類 | 意味 | 主な発生箇所 | UI扱い |
|---|---|---|---|
| Validation | 入力・条件不正 | Policy / UseCase | 項目または画面内 |
| Business | 業務上許可されない状態 | Domain / UseCase | 画面またはDialog |
| LocalStorage | DataStore / Room / File 失敗 | Repository / DataSource | Dialog / Retry |
| Network | 通信前後の接続失敗 | Network / Gateway | Retry |
| Api | API が返したエラー | Gateway / Repository | Dialog / Retry |
| ApiInvalidResponse | 応答形式不正 | Mapper / Gateway | Dialog / Retry |
| Unexpected | 未分類例外 | 共通境界 | Dialog / 調査 |

## 10.2 復旧属性

| エラー | 復旧 |
|---|---|
| Validation | 入力修正 |
| LocalStorage | 再試行、設定確認 |
| Network / Api | 再試行、通信確認 |
| Unexpected | 再起動、ログ調査 |

## 10.3 エラーコード体系

エラーコードは文字列として安定させ、画面文言とは分離する。具体的なコード一覧は詳細設計書で定義する。`cause` は調査用途に保持できるが、利用者へ直接表示しない。

## 10.4 Error と UI の対応

```text
AppError
  -> Feature の UiError Mapper / Message Factory
  -> UiState の表示用エラーまたは UiEffect
  -> Route / Screen が表示
```

# 11. データと永続化設計

## 11.1 保存方針

| データ | 保存方式 | 理由 |
|---|---|---|
| 軽量設定 | DataStore Preferences | 小さなキー・バリュー値を購読・保存するため |
| 操作履歴 | Room | 一覧、検索、種別取得、保持期間削除が必要なため |
| テーマ | DataStore Preferences | アプリ全体の設定として保持するため |
| 法務文書 | raw resource | アプリ同梱の本文を扱うため |
| OSS License | License Provider | 導入ライブラリから情報を取得するため |

## 11.2 保存単位および保存方式

- DataStore ファイル名は App 側で決定し、Core は保存契約を提供する。
- Room の Database、Entity、DAO は App / Feature の組み合わせで決定する。
- Core の Database 共通処理は Feature 固有の Entity を知らない。
- Repository が保存方式を隠蔽し、上位層へ Domain Model または AppResult を返す。

## 11.3 Operation Log 論理構造

| 項目 | 内容 |
|---|---|
| id | DB採番の識別子 |
| type | Screen / Action / Setting / Upload / Download / Search / Error / System |
| result | Success / Failure / Warning / Info |
| title | 必須の短い説明 |
| summary | 概要 |
| detail | 詳細 |
| occurredAtMillis | 発生時刻 |
| correlationId | 関連処理識別子 |

## 11.4 読込および反映タイミング

- Settings は画面表示時に保存値を購読する。
- Theme Settings は AppRoot が購読し、全画面へ適用する。
- History は画面表示時に操作履歴を購読する。
- Legal / License / Version は画面表示時または Retry 時に取得する。

## 11.5 排他・整合性

- DataStore はアプリ全体で共有する単一の保存先を利用する。
- Room 操作は共通の Database Executor / Transaction 境界を利用できる。
- 保存エラーは AppResult Failure として上位へ返す。
- Entity と Domain の変換は Mapper に分離する。

## 11.6 データ保持ポリシー

操作ログの削除処理と保持日数の計算は提供するが、自動実行の契機は現行サンプルでは未確定である。実案件で保持日数、削除スケジュール、全削除操作の権限を決定する。

# 12. ログ記録設計

## 12.1 操作ログイベント

| Event | Type | Result | 記録契機 |
|---|---|---|---|
| HomeDisplayed | Screen | Info / Success | Home 取得成功 |
| SettingChanged | Setting | Success | 設定保存成功 |
| SettingSaveFailed | Error | Failure | 設定保存失敗 |
| ScreenLoadFailed | Error | Failure | 主要画面の取得失敗 |

## 12.2 アプリログ

アプリログは AppLogger を経由する。Timber の Tree 初期化は Application 起動時に行い、Debug / Release の出力方針を App 側で指定する。

## 12.3 ログ記録方針

- ログ文言とユーザー表示文言を分離する。
- エラーコード、処理対象、結果を必要な範囲で記録する。
- cause は調査に必要な場合のみ記録する。
- トークン、個人情報、文書本文など機微情報を記録しない。
- 操作ログ保存失敗は Warning としてアプリログへ出し、本来の処理を継続できる構造とする。

# 14. 設計原則

## 14.1 責務分離原則

- Screen は表示と Event 通知に限定する。
- Route は ViewModel 取得、State / Effect 購読、Navigation、Dialog、Snackbar を担当する。
- ViewModel はイベントを解釈し、UseCase、Message、Reducer、Effect を接続する。
- UseCase はアプリケーション操作を組み立てる。
- Domain / Policy は業務上の意味と判定を扱う。
- Repository は保存方式を隠蔽する。
- Gateway / Provider は外部サービスや Android API を隠蔽する。
- Reducer は副作用を持たない。

## 14.2 共通化の判断

共通化は、同じ処理に見えるかではなく、同じ理由で変更されるかを基準に判断する。BaseViewModel は状態・イベント・Effect の基礎機能に限定し、自動 Loading、汎用 ErrorHandler、汎用 UseCase 基底クラスなどを持たせない。

## 14.3 命名

- Interface に `I` prefix を付けない。
- Repository は `SampleRepository` / `SampleRepositoryImpl` の形式とする。
- Gateway は `SampleGateway` / `SampleGatewayImpl` の形式とする。
- Result は Kotlin 標準 Result ではなく AppResult を利用する。
- Intent ではなく UiEvent を基本用語とする。

# 15. 詳細設計に向けたアーキテクチャ適用規定

## 15.1 Event / Message / State / Effect

- Event は画面で発生した入力または表示開始を表す。
- Message は処理結果を State 更新へ渡す。
- State は継続表示する値を保持する。
- Effect は一度だけ実行する処理を表す。

## 15.2 Reducer

Reducer は現在 State と Message を受け取り、新しい State を返す。I/O、ログ、Navigation、時刻取得、例外処理は Reducer で行わない。

## 15.3 Event Queue

BaseViewModel は UiEvent の入力口を提供し、Channel.BUFFERED へ積んだ Event を順番に処理する。View / Screen / Route は ViewModel のイベント処理本体を直接呼ばない。

## 15.4 Error 変換

AppError は処理失敗の意味を表し、表示文言を直接保持しない。Feature の Presentation 側で UiError や表示メッセージへ変換し、画面への表示方法を決定する。

## 15.5 DI

- Application 共通依存は SingletonComponent へ登録する。
- Feature 固有依存は Feature の DI Module に登録する。
- 契約と実装の結合は App / Feature の DI で行う。
- テストでは Fake / Stub を差し替えられる契約を優先する。
