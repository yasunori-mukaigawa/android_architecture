# プレゼンテーション層 共通設計思想ガイド

## 🧭 この文書の使い方

### 🎯 この文書の役割

本ドキュメントは、特定の言語・UIフレームワークに依存しない、  
プレゼンテーション層の **背景となる思想（憲法）** を定義するものです。

Windows、Android、iOS、Flutter、React、Vue、Angular など、  
利用する技術スタックが変わっても、画面設計・状態管理・責務分離・副作用制御を  
同じ考え方で判断できるようにすることを目的とします。

この文書は、**実装手順書ではありません**。

実装の正誤だけでなく、以下を判断するために使用します。

- なぜその責務に分けるのか
- なぜその依存方向にするのか
- なぜその処理をそこに書くべきなのか
- なぜその実装が将来の変更に耐えられるのか
- なぜその設計を他者に説明できるのか

> [!IMPORTANT]
> **「この文書は、技術スタックをまたいだ最終判断基準である」**
>
> 各技術別のカスタマイズ設計書で判断に迷った場合は、  
> 必ず本書の「なぜそうするのか」に戻ること。

### 📌 この章はこういうときに見る

- 「技術が違っても同じ思想で設計できるようにしたい」とき 
- 「View / ViewModel / Store / Controller の責務が分からない」とき
- 「State と Effect の違いが曖昧になった」とき
- 「UseCase / Domain / Repository / Gateway の境界に迷った」とき
- 「画面側にどこまでロジックを書いてよいか」判断したいとき
- 「レビューで違和感があるが、うまく言語化できない」とき
- 「既存コードをリファクタリングする際、どこをどう分離すべきか判断したい」とき

# 🛠 設計ルールの真意と背景

以下は、プレゼンテーション層における「設計ルールの意図」を明文化したものです。

単なるルールの羅列ではなく、  
 **「なぜこのルールがあるのか」** という思想を理解し、  
技術スタックをまたいだ品質向上を目指します。


## 第①章：技術が変わっても、設計で見るものは変わらない

### 👁 核心的な考え方

UI技術や言語は変わっても、アプリケーション開発で扱う設計上の関心は大きく変わりません。

画面は、基本的に次の流れで動きます。

```text
ユーザーが操作する
↓
操作を入力事実として受け取る
↓
必要な処理を実行する
↓
結果を状態に反映する
↓
画面を更新する
↓
必要に応じて、一度だけの副作用を実行する
```

この流れは、Windowsアプリでも、Androidでも、iOSでも、Flutterでも、Reactでも同じです。

違うのは、書き方・ライブラリ・フレームワークの表現です。  
設計上の問いは共通です。

### 💡 なぜそう考えるのか

SIer や受託開発では、案件ごとに技術スタックが変わることがあります。

そのたびに、設計思想まで毎回変えていると、以下の問題が起きます。

- 新規参画時の学習コストが高くなる
- レビュー観点が案件ごとに変わる
- 品質が属人化する
- 技術者が別プロジェクトへ移動しにくくなる
- 同じような設計ミスを毎回繰り返す
- 案件ごとに「その場限りの作法」が増える

そのため、技術ごとの実装差分は認めつつ、  
設計で見る観点は共通化します。

### 🎯 共通して扱う設計上の問い

| 観点 | 問い |
|---|---|
| 入力 | ユーザーは何をしたのか |
| 状態 | 画面や機能は今どのような事実を持っているのか |
| 処理 | どの業務処理を実行するのか |
| 結果 | 処理結果をどのように状態へ反映するのか |
| 副作用 | 画面遷移・ダイアログ・通知などをどう扱うのか |
| 責務 | その処理はどの役割が持つべきか |
| 依存 | どちらがどちらを知ってよいのか |
| 変更 | 仕様変更時にどこを直せばよいのか |
| 説明 | なぜその設計にしたのか説明できるか |

> [!IMPORTANT]
> **「技術スタックは変わっても、設計で見るものは変えない」**
>
> 個別技術の学習は必要です。  
> しかし、設計の見方まで毎回変える必要はありません。

## 第②章：共通アーキテクチャモデル

### 🏗 基本構造

プレゼンテーション層を中心とした基本構造は、次のように整理します。

```text
View / UI Component
    ↓ User Action / Intent
Presentation Controller
    ↓ UseCase呼び出し
UseCase
    ↓ Repository / Gateway
External Resource

UseCase
    ↓ Result
Presentation Controller
    ↓ Message / State Update
State
    ↓ Render / Binding
View / UI Component

Presentation Controller
    ↓ Effect
Effect Handler / UI Runtime
```

### 🧩 主要概念

| 共通概念 | 役割 |
|---|---|
| View / UI Component | 表示とユーザー操作の検知を行う |
| User Action / Intent | ユーザーが何をしたかを表す入力事実 |
| Presentation Controller | 入力を受け取り、UseCase呼び出し・State更新・Effect発行を制御する |
| UseCase | アプリケーションとしての処理手順を表す |
| Domain | 業務上の不変条件・値の正しさを表す |
| Repository | 業務データの取得・保存を隠蔽する |
| Gateway | 外部サービス・SDK・APIとの接続を隠蔽する |
| State | 画面が保持すべき事実を表す |
| Message | State変更の理由・結果を表す |
| Reducer | 現在のStateとMessageから新しいStateを作る |
| Effect | 一度だけ実行される副作用を表す |
| Effect Handler | Effectを実際の画面遷移・通知・ダイアログに変換する |

### 🔁 技術別名称の違い

共通思想上は同じ役割でも、技術によって名前が異なります。

| 共通概念 | Windows | Android | iOS / SwiftUI | Flutter | React |
|---|---|---|---|---|---|
| View / UI Component | XAML / View | Composable / Fragment | SwiftUI View | Widget | Component |
| Presentation Controller | ViewModel | ViewModel | ObservableObject / ViewModel | Notifier / Bloc / Cubit | Store / Container / Hook |
| State | ViewModel State | UiState / StateFlow | Observable State | State class | Store State |
| Intent | Command / Event | UiEvent / Intent | View Action | Event / Method | Action / Event Handler |
| Message | Message | UiMessage / StateMutation | Mutation / Action Result | State Change Event | Action / Reducer Payload |
| Reducer | Reducer | Reducer / copy | reduce相当処理 | reducer / copyWith | Reducer |
| Effect | UiEffect | SharedFlow / Channel | Alert / Navigation Event | Effect stream | Toast / Router Effect |
| UseCase | UseCase class | UseCase class | UseCase protocol | UseCase class | UseCase function / class |
| Repository | Repository | Repository | Repository | Repository | Repository / API Client |
| Gateway | Gateway | Gateway / DataSource | Gateway / Client | Gateway / Client | Gateway / Client |
| Dependency Wiring | DI / Registrar | Hilt / Koin | Factory / DI Container | Riverpod / Provider | Context / DI / Factory |

> [!IMPORTANT]
> **「名前を揃えること」が目的ではない**
>
> 重要なのは、各技術の用語が違っても、  
> 責務の分け方を同じ思想で判断すること。

## 第③章：View / UI Component は入力の発火点に限定する

### 👁 核心的な役割

View / UI Component は、画面表示とユーザー操作の検知に責務を限定します。

やることは次の通りです。

- Stateを表示する
- ユーザー操作を検知する
- ユーザー操作を User Action / Intent として通知する
- 純粋なUI表現を行う

やらないことは次の通りです。

- 業務判断をする
- UseCaseを直接呼ぶ
- Repository / Gateway / API Client を直接呼ぶ
- DB / API / SDK に直接触る
- 成功 / 失敗 / 次状態を判断する
- 状態更新の理由を決める

### 💡 なぜそうするのか

UIと業務ロジックは変更理由が異なります。

UIは、画面デザイン、入力部品、レイアウト、UX改善によって変わります。  
業務ロジックは、仕様、業務ルール、外部連携、データ構造によって変わります。

この2つを混ぜると、UI変更のたびに業務ロジックが壊れ、  
業務仕様変更のたびに画面が壊れます。

View / UI Component は、あくまで入力の発火点であり、判断者ではありません。

### ⚖️ 例外的に許容されるケース

以下は、UI責務に閉じるため許容します。

- 見た目だけの制御
- フォーカス制御
- アニメーション
- スクロール制御
- 入力補助
- UI部品固有のイベント変換
- 業務意味を持たないフォーマット補助

ただし、入力補助であっても業務的な意味を持つ場合は、Viewに書いてはいけません。

### 🚫 境界を越えているサイン

次の状態になっている場合、View / UI Component の責務を越えています。

- UI内に業務条件の `if` / `switch` がある
- API / DB / SDK を直接呼んでいる
- 保存可否・登録可否・遷移可否を判断している
- エラーメッセージを直接組み立てている
- 成功時 / 失敗時の業務分岐を持っている

> [!IMPORTANT]
> **「Viewは結果を知らない」**
>
> Viewが知ってよいのは「ユーザーが何をしたか」までであり、  
> 「その結果何が起きるか」は知らない。

## 第④章：Presentation Controller は司令塔に限定する

### 🏗 Presentation Controller とは

Presentation Controller とは、Viewからの入力を受け取り、  
State更新・UseCase呼び出し・Effect発行を制御する役割を指します。

技術によって、次のような名前になります。

- ViewModel
- Presenter
- Controller
- Store
- Notifier
- Bloc / Cubit
- Container
- Hook Controller

名前は違っても、役割は同じです。

### 🎯 核心的な役割

Presentation Controller は、画面単位の司令塔です。

主な責務は次の通りです。

- User Action / Intent を受け取る
- 必要な UseCase を呼び出す
- UseCaseの結果を Message に変換する
- Messageをもとに State を更新する
- 画面遷移・ダイアログ・通知などの Effect を発行する
- UI表示用エラーや文言変換を、専用の変換器へ委譲する

### 🚫 やらないこと

Presentation Controller は、次の責務を持ってはいけません。

- 業務ルールそのものを実装する
- DB / API / SDK に直接触る
- Repository / Gateway の具体実装を知る
- 画面表示文言を直接組み立てる
- 複数データを自分で組み合わせて業務判断する
- Stateを理由なく直接書き換える

### 💡 なぜそうするのか

Presentation Controller は、画面と業務処理の接続点です。

ここに業務ロジックや外部I/Oを詰め込むと、画面単位の巨大クラスになります。

その結果、次の問題が起きます。

- 画面ごとに似た処理がコピーされる
- 業務仕様変更の影響範囲が広がる
- テストが難しくなる
- UI変更と業務変更が分離できなくなる
- 新しい技術スタックへ移植しにくくなる

Presentation Controller は、自分で処理を完結させる場所ではありません。  
どこに任せるかを決める交通整理役です。

> [!IMPORTANT]
> **「Presentation Controller は交通整理のみ」**
>
> 自分で全部やるのではなく、  
> 処理を適切な責務へ振り分ける。

## 第⑤章：State / Intent / Message / Reducer / Effect を分離する

### 🧭 この章の目的

この章では、画面設計における以下の概念を整理します。

- Intent / User Action
- State
- Message
- Reducer
- Effect

これらを混同すると、状態変更の理由が追えなくなり、  
再描画・画面遷移・ダイアログ・通知などでバグが起きやすくなります。

### 5.1 Intent / User Action

Intent / User Action は、ユーザーが何をしたかを表す入力事実です。

例：

- 保存ボタンを押した
- 入力値を変更した
- 一覧項目を選択した
- 初期表示を開始した
- 戻るボタンを押した

Intent は、状態変更そのものではありません。  
あくまで状態変更のきっかけです。

### 5.2 State

State は、画面が保持すべき事実です。

例：

- 入力値
- 選択値
- 一覧データ
- ローディング状態
- バリデーション結果
- ボタン活性
- 表示するエラー情報

State は、再描画・再購読・画面復元が発生しても、同じ意味で扱える情報です。

### 5.3 Message

Message は、State変更の理由または処理結果を表すものです。

例：

- 初期表示を開始した
- データ取得に成功した
- データ取得に失敗した
- 入力検証結果が更新された
- 保存処理が完了した

Message は、ユーザー操作そのものではありません。  
UseCaseやPresentation Controllerの処理結果を、State更新の文脈へ変換したものです。

### 5.4 Reducer

Reducer は、現在の State と Message から、新しい State を生成する役割です。

Reducer は、次の性質を持つべきです。

- 副作用を持たない
- 外部I/Oを呼ばない
- 非同期処理をしない
- 同じ入力に対して同じ出力を返す
- State変更の理由をMessageとして受け取る

Reducer は、状態計算の専門家です。

### 5.5 Effect

Effect は、一度だけ実行される副作用です。

例：

- 画面遷移
- ダイアログ表示
- Toast / Snackbar 表示
- 外部アプリ起動
- ファイルダウンロード開始
- クリップボードコピー

Effect は State に入れてはいけません。

State に入れると、再描画・再購読・画面復元時に  
何度も実行される可能性があるためです。

### 5.6 State と Effect の判断基準

| 判断 | State | Effect |
|---|---|---|
| 保持され続けるべきか | はい | いいえ |
| 再描画で再利用してよいか | はい | いいえ |
| 一度だけ実行したいか | いいえ | はい |
| 画面の現在状態を表すか | はい | いいえ |
| 通知・遷移・ダイアログか | 原則いいえ | はい |

### ⚠️ 典型的な誤り

```text
ShouldNavigate = true
IsDialogOpen = true
ShowToast = true
SaveCompleted = true
```

これらは、多くの場合 State ではなく Effect として扱うべきです。

> [!IMPORTANT]
> **「状態と副作用を混ぜない」**
>
> 画面に残る事実は State。  
> 一度だけ起こす処理は Effect。

## 第⑥章：UseCase / Domain の責務を分離する

### 🎯 Domain の責務

Domain は、業務上の不変条件・値の正しさ・概念の意味を表します。

Domain が扱うものは、技術・画面・DB・APIに依存しません。

例：

- 金額は0以上である
- メールアドレスは形式を満たす
- 期間の開始日は終了日以前である
- ステータス遷移には許可された順序がある
- 本人確認結果には判定根拠が必要である

Domain は、業務の真実を表す場所です。

### 🧭 UseCase の責務

UseCase は、アプリケーションとしての処理手順を表します。

例：

- ユーザーを登録する
- 設定値を読み込む
- 外部APIへ問い合わせる
- 保存前に検証し、成功時にRepositoryへ保存する
- 複数のRepository / Gatewayを組み合わせて処理する

UseCase は、Domainを利用し、Repository / Gatewayを通じて外部世界と接続します。

ただし、UseCase は UI を知ってはいけません。

### ⚖️ Domain と UseCase の判断基準

| 処理 | 置き場 |
|---|---|
| 値単体で完結するルール | Domain |
| 業務上の不変条件 | Domain |
| 複数データを組み合わせる処理 | UseCase |
| Repository / Gateway を呼ぶ処理 | UseCase |
| アプリケーションとしての手順 | UseCase |
| UI表示文言の決定 | Presentation側 |
| 画面遷移 | Effect |

### 🚫 境界を越えているサイン

- UseCase に画面名が入っている
- UseCase が UI文言を返している
- Domain が DB / API に依存している
- Domain が画面表示用プロパティを持っている
- Presentation Controller が業務ルールを直接判定している

> [!IMPORTANT]
> **「Domainは真実、UseCaseは手順」**
>
> この2つが混ざると、設計は必ず崩れる。

## 第⑦章：Repository / Gateway は外部世界との境界である

### 🧱 Repository の責務

Repository は、業務データの取得・保存を隠蔽する境界です。

Repository の利用者は、データがDBから来るのか、ファイルから来るのか、  
メモリから来るのかを知る必要がありません。

Repository がやること：

- 業務データを取得する
- 業務データを保存する
- 永続化方式を隠蔽する
- 永続化形式とDomain / Application用モデルを変換する

Repository がやらないこと：

- 業務判断
- UI表示判断
- 画面状態の更新
- API通信そのものの複雑な手順制御

### 🌐 Gateway の責務

Gateway は、外部サービス・SDK・API・デバイスなど、外部世界との通信を隠蔽する境界です。

Gateway がやること：

- 外部APIを呼び出す
- SDKを呼び出す
- デバイスと通信する
- 外部仕様をアプリ内で扱いやすい形へ変換する

Gateway がやらないこと：

- UI判断
- 画面状態の更新
- 業務手順全体の制御
- 仕様上の最終判断

### ⚖️ Repository / Gateway の判断基準

| 対象 | 置き場 |
|---|---|
| 業務データの取得・保存 | Repository |
| DB / ファイル / ローカルストレージ | Repository |
| REST API / GraphQL / SDK / デバイス | Gateway |
| 外部仕様のDTO変換 | Gateway / Infrastructure |
| 業務判断 | UseCase |
| 表示判断 | Presentation |

### 🚫 境界を越えているサイン

- Repository 内に業務条件が固定されている
- Gateway が画面表示用の文字列を返している
- UseCase が SQL / URL / SDK の詳細を知っている
- Presentation Controller が API Client を直接呼んでいる
- Repository が保存可否を判断している

> [!IMPORTANT]
> **「Repository / Gateway は窓口であって判断者ではない」**
>
> 判断は UseCase または Domain に戻す。

---

## 第⑧章：エラーハンドリングは構造で扱う

### 🚨 原則

エラーは、文字列・bool・nullで曖昧に表現してはいけません。

失敗理由は、構造として扱います。

```text
Exception
→ UseCase / Boundary で捕捉
→ DomainError / ApplicationError
→ Result
→ Presentation Controller
→ UiError / PresentationError
→ State / Effect
→ 表示
```

### 🧩 エラーの層分離

| 概念 | 役割 |
|---|---|
| Exception | 技術的な例外 |
| DomainError | 業務的な失敗理由 |
| ApplicationError | アプリケーション処理上の失敗理由 |
| Result | 成功 / 失敗を戻り値として表現する構造 |
| UiError / PresentationError | 画面表示用のエラー情報 |

### 💡 なぜそうするのか

- 失敗理由をテスト可能にするため
- UI文言と失敗意味を分離するため
- 例外を制御不能なフローから排除するため
- 画面ごとのエラー表示ばらつきを防ぐため
- ログ・表示・復旧導線を一貫させるため

### 🚫 やってはいけないこと

- `return false` で失敗を表す
- `return null` で失敗を表す
- `return "エラーです"` で失敗を表す
- UseCase が UI文言を返す
- Presentation Controller が Exception 型を直接分岐する
- View が catch してダイアログを出す

> [!IMPORTANT]
> **「例外は構造に変換してから扱う」**
>
> UIに届く時点では、表示可能な情報へ変換されているべきである。

---

## 第⑨章：共通化・抽象化は「変化理由」で判断する

### 🛑 原則

共通化は、似ているから行うものではありません。

共通化してよいのは、**同じ理由で変更されるもの**です。

### ⚖️ 判断基準

次の問いに答えられる場合、共通化を検討できます。

- 同じ理由で変更されるか
- 同じテストケースで検証できるか
- 呼び出し側が内部条件を知らなくても使えるか
- 抽象化によって理解が簡単になるか
- 新しい種類が増えたとき、既存コードを壊さず追加できるか

### 🚫 共通化してはいけないサイン

- boolフラグで振る舞いを切り替えている
- `if` / `switch` が増え続けている
- 抽象の利用者が内部事情を知らないと使えない
- 似ているだけで変更理由が違う
- 実装が1つしかないのに抽象だけが存在する
- 共通化した結果、テストが複雑になっている

> [!IMPORTANT]
> **「抽象化は理解を助けるためのもの」**
>
> 理解を難しくする抽象化は、設計ではなく負債である。

---

## 第⑩章：Dependency Wiring / Dependency Injection は構造を表現する場所である

### 🧩 Dependency Wiring とは

Dependency Wiring とは、アプリケーションの依存関係を組み立てる場所です。

技術によって、次のような形になります。

- DI Container
- ServiceCollection
- Provider
- Riverpod Provider
- Hilt Module
- Factory
- Context Provider
- Composition Root

名前は違っても、目的は同じです。

### 🎯 原則

依存関係の組み立ては、アーキテクチャを表現する場所です。

そのため、次の原則を守ります。

- レイヤごとに登録責務を分ける
- Composition Root は束ねるだけにする
- 上位層が下位層の具体実装を直接知りすぎないようにする
- 依存方向を見れば、アーキテクチャが分かる状態にする
- テスト時に差し替え可能な構造にする

### 🚫 やってはいけないこと

- 画面内で具体実装を `new` する
- Composition Root に全登録をベタ書きする
- UI層がInfrastructureの具体実装に直接依存する
- Repository / Gateway の実装をPresentation側が知る
- 依存関係の理由を説明できない

> [!IMPORTANT]
> **「DIは依存の地図」**
>
> ここを見れば、アプリケーションの構造が分かる状態にする。

---

## 第⑪章：UI表現ロジックは分離する

### 🎨 UI表現ロジックとは

UI表現ロジックとは、業務上の意味を画面表示へ変換する処理です。

例：

- DomainError を画面用エラーメッセージへ変換する
- 業務ステータスをラベル文言へ変換する
- 復旧ガイダンスを組み立てる
- Severity をアイコンや色へ変換する
- 表示用フォーマットを決める

### 💡 なぜ分離するのか

UI表現ロジックをPresentation Controllerへ直接書くと、  
Presentation Controllerが肥大化します。

また、画面ごとに文言や表示ルールがばらつきます。

そのため、UI表現ロジックは専用の変換器・Resolver・Formatter・Presenterへ分離します。

### ⚖️ 判断基準

| 処理 | 置き場 |
|---|---|
| 業務的な失敗意味 | Domain / UseCase |
| 表示用エラー文言 | UI Error Resolver |
| 復旧ガイダンス | Message Builder / Guidance Builder |
| 入力値の業務検証 | Domain / UseCase |
| 入力欄の見た目制御 | View / UI Component |
| ボタン活性根拠 | State / Derived State |
| Toast / Dialog 表示 | Effect |

> [!IMPORTANT]
> **「意味と表示を分ける」**
>
> DomainError は意味。  
> UiError は表示。

# ✅ レビュー観点

## 第⑫章：レビューでは構造を見る

レビューでは、コードが動くかだけではなく、次の観点を確認します。

### 12.1 責務

- Viewが業務判断を持っていないか
- Presentation Controllerが業務ロジックを持っていないか
- UseCaseがUI都合を知っていないか
- Repository / Gatewayが判断者になっていないか
- Domainが外部依存を持っていないか

### 12.2 依存

- 依存方向は一方向か
- UI層がInfrastructureを直接参照していないか
- UseCaseが具体的なDB / API / SDKを知っていないか
- DI / Wiringを見れば構造が分かるか

### 12.3 状態

- Stateは保持すべき事実だけを持っているか
- EffectをStateで表現していないか
- State変更の理由がMessageとして説明できるか
- Reducerが副作用を持っていないか

### 12.4 エラー

- 失敗理由が型で表現されているか
- bool / null / string で失敗を返していないか
- UI文言と失敗意味が分離されているか
- 異常系がテスト可能か

### 12.5 変更容易性

- 仕様追加時にどこを直せばよいか説明できるか
- 新しい種類が増えたとき、既存コードを壊さず追加できるか
- 変更理由が異なるものを無理に共通化していないか
- 抽象化が理解を助けているか

# ☠️ アンチパターン集

## 第⑬章：設計崩れの典型例

この章は、実装時に陥りやすい **設計崩れの典型例** をまとめたものです。

正解だけを見ると「守る」ことはできても、  
「なぜそれが危険なのか」が腹落ちしにくいことがあります。

そのため本章では、**やってはいけない実装の型**を明示し、  
どの責務が崩れているのかを理解することを目的とします。

## 13.1 Viewに業務ロジックを書く

### ❌ アンチパターン

```pseudo
onSaveButtonClick:
    if input.price < 1000:
        showError("1000円未満は登録できません")
        return

    saveData()
```

### 🔥 何が壊れているか

- Viewが業務ルールを知っている
- Viewが保存可否を判断している
- UIを通さないとテストできない
- 画面が変わると業務ロジックも壊れる

### ✅ 修正方針

- Viewは SaveClicked Intent を送るだけにする
- 検証はDomain / UseCaseへ移動する
- 結果はState / Effectで表現する

## 13.2 Presentation Controller が巨大化する

### ❌ アンチパターン

```pseudo
handleSave:
    tax = price * 0.1
    total = price + tax
    db.save(total)
    navigateToCompletePage()
```

### 🔥 何が壊れているか

- 計算、保存、遷移が混ざっている
- 業務ロジックが画面に閉じる
- DB変更がUIに波及する
- テストが難しくなる

### ✅ 修正方針

- 計算ルールはDomainへ移動する
- 保存手順はUseCaseへ移動する
- DBアクセスはRepositoryへ移動する
- 遷移はEffectへ分離する

## 13.3 EffectをStateで表現する

### ❌ アンチパターン

```pseudo
state.shouldNavigate = true
state.showDialog = true
```

### 🔥 何が壊れているか

- 再描画時に再実行される
- 画面復元時に意図しない副作用が起きる
- 状態とイベントの意味が混ざる

### ✅ 修正方針

- 遷移・ダイアログ・通知はEffectとして発行する
- Stateには表示上保持すべき事実のみを持たせる

## 13.4 Repository が業務判断を持つ

### ❌ アンチパターン

```pseudo
repository.getActiveUsers()
```

### 🔥 何が壊れているか

- RepositoryがActiveの意味を知っている
- 条件違いの取得メソッドが増える
- UseCase側で業務判断を制御できない

### ✅ 修正方針

- Repositoryは取得・保存に限定する
- 業務条件はUseCaseまたはDomainで判断する
- 条件は引数やQuery Objectとして渡す

## 13.5 似ているだけで共通化する

### ❌ アンチパターン

```pseudo
execute(type):
    if type == A:
        doA()
    if type == B:
        doB()
```

### 🔥 何が壊れているか

- 変更理由が異なる処理を一つに押し込んでいる
- 種類が増えるたびに分岐が増える
- 呼び出し側が内部仕様を知らないと使えない

### ✅ 修正方針

- 同じ理由で変わるものだけ共通化する
- 種類ごとに責務を分ける
- Strategy / State / Factory などの適用を検討する

> [!TIP]
> ## アンチパターンまとめ
>
> 設計崩れの多くは、次の3つに集約されます。
>
> ```text
> ① 責務を混ぜる
> ② レイヤを飛び越える
> ③ 状態と副作用を混同する
> ```
>
> 実装時に迷ったら、まずは以下を確認すること。
>
> - これは誰の責務か？
> - この処理は保持すべき状態か、一回だけの副作用か？
> - この依存は本当にこのレイヤが持つべきか？

共通設計思想を各技術へ展開する際は、次の順で整理します。

### 14.1 技術別に決めること

# 🏁 最終判断基準

## 第⑮章：迷ったらこの問いに戻る

実装やレビューで迷ったら、最後は次の問いに戻ります。

```text
1. これは誰の責務か？
2. これは保持すべき状態か、一度だけの副作用か？
3. これは業務判断か、UI表現か、外部接続か？
4. この依存方向は説明できるか？
5. 仕様変更時にどこを直せばよいか説明できるか？
6. この抽象化は理解を助けているか？
7. なぜこの設計にしたのか説明できるか？
```

この問いに答えられない場合、その実装はまだ設計として十分に整理されていません。

> [!IMPORTANT]
> **「設計とは、コードの形ではなく、変更理由と責務を説明できる状態である」**

# 📝 まとめ

この共通設計思想ガイドが目指すのは、特定技術に閉じた実装ルールではありません。

目指すのは、技術スタックが変わっても、同じ設計思想で判断できる状態です。

Windowsアプリでも、Androidでも、iOSでも、Flutterでも、Reactでも、扱うべき問いは変わりません。

- ユーザーは何をしたのか
- 状態はどこにあるのか
- 業務処理はどこにあるのか
- 副作用はどう扱うのか
- 依存はどちらを向いているのか
- 変更時にどこを直せばよいのか
- なぜその設計にしたのか説明できるか

この問いを共通化することで、メンバーは技術スタックが変わっても、  
毎回ゼロから設計思想を覚え直さずに済みます。

個別技術の学習は必要です。  
しかし、設計の見方まで毎回変える必要はありません。

> [!IMPORTANT]
> **「技術スタックは変わっても、設計で見るものは変えない」**
>
> それが、案件をまたいで人が動ける組織を作るための前提である。

# 適用範囲と限界

本ガイドは、主に以下の場面で効果を発揮する。

- 新規開発
- フルスクラッチ開発
- 新規画面追加
- 共通基盤設計
- 技術スタック移行時の設計標準化
- レビュー観点の統一

一方で、既存システムの保守開発に対して、
本ガイドの構造をそのまま全面適用することは推奨しない。

既存システムでは、過去の設計判断、納期、予算、技術制約、既存コード量により、
理想構造へ一気に移行できない場合が多い。

そのため保守開発では、本ガイドを「全面適用するルール」ではなく、
設計崩れを見つけるための診断観点として利用する。

重要なのは、既存コードを否定することではなく、
今後の変更でこれ以上構造を崩さないこと、
そして変更機会に合わせて少しずつ責務を分離していくことである。
